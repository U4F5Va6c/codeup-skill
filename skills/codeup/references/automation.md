# 状态联动与事件唤醒

配置前读取项目 tracker 的状态映射、现有规则及模板来源。先确定事件方向、触发条件、动作与负责方，再选入口；以下平台能力于 2026-10-11 对照官方文档核对，具体选项仍以目标项目为准。

## 三条不同的事件链路

| 目的 | 路径 | 所需配置 |
|---|---|---|
| 根据父子、普通关联或依赖项的变化更新工作项 | ProjeX → ProjeX 自动化规则 | 真实关系与相应规则；普通关联也可联动，但不因此变成有向依赖 |
| 根据提交/MR 事件更新工作项 | Codeup Webhook → ProjeX 内置接收端 → DevOps 联动规则 | 项目提供的 URL/Secret 配到相关代码库，并建立工作项与代码对象的原生关联；无需自建接收服务 |
| 工作项变化后通知或唤醒外部 Agent | ProjeX 自动化 → 外部 Webhook 接收端 → 调度器 | 可达的接收服务、鉴权、事件去重、任务领取与授权范围；不是配置 Codeup 联动后自动获得的能力 |

Flow 监听代码事件触发 CI 是另一个订阅。已有 Flow Webhook、项目已关联仓库或正文包含链接，都不能证明 ProjeX 的 MR 事件联动已配置。Webhook 传递事件，自动化规则决定状态动作；两者都不能替代 Codeup 合并门禁。

## Codeup → ProjeX：推荐按需启用

未配置时，Agent/人工仍可通过 CLI 读取 MR、测试结果并按映射更新工作项；代码与 MR 操作不受此阻碍，但会话结束后发生的事件需要下次主动核对。配置后，符合规则的代码事件可在 Agent 不在线时推进状态，并留下自动化执行记录；它不会自行接着写代码或判断业务验收。

1. 在 ProjeX **项目设置 → Webhook** 获取该项目的 Codeup 集成配置，核实项目与代码库范围。在各相关 Codeup 仓库的 Webhook 设置中使用项目提供的 URL、Secret Token 和需要的事件（MR 联动需合并请求事件，提交联动再订阅推送）。查重并保留其他用途的 Hook。
2. 在 ProjeX **自动化规则 → DevOps 联动** 选择实际支持的事件、条件和动作；先限定工作项类型、来源状态及仓库/目标分支范围（若界面支持）。若无法表达必要的限定，不启用宽泛规则，继续由 Agent/人工核验。
3. 优先自动化低歧义的中间状态，例如已关联开发分支/MR 后进入开发中。全体必需 MR 合并后进入待验收，仅在关联范围完整、事件确实代表合并且规则能表达条件时启用。文档中的“已通过”示例不能未经回读就等同于“已合并”。
4. 用获准测试事件验证投递、规则执行日志和工作项回读；再验证 MR 仅创建/批准但未合并、合入错误目标、另一必需仓库未完成时不会提前关闭。规则保存成功或 Webhook 连通性测试成功不等于业务条件正确。

“所有已关联 MR”不等于“所有必需 MR”：遗漏尚未创建/关联的交付会导致提前推进。跨仓库需求先明确交付集合；父需求默认保留到整体验收，避免直接照抄“全部 MR 通过 → 需求完成”模板。规则只看 MR/状态时，也不能证明当前 SHA 测试、发布或业务验收完成。

### 首条规则：关联 MR → 开发中

使用项目已有状态：例如任务的“待处理 → 处理中”，其中“处理中”映射开发中。条件限定为“任务新增合并请求关联，且当前仍为待处理”，避免已完成任务回退；父需求按整体验收推进。

先启用规则并配置 Codeup → ProjeX Webhook，再用 `codeup-create-change-request --work-item-ids` 创建带原生关联的 MR。2026-10-11 隔离项目实测，此路径触发了规则；同一 MR 关联的已完成任务和需求未被改动。验收时同时查看 Webhook 投递、自动化执行日志与工作项最终状态。

同次实测中，使用 `projex-create-workitem-ext-relation-record` 给已有 MR 补关联，随后更新该 MR，并未触发此规则。该 API 可维护原生关联，但不能据此承诺相同的事件行为，也不能假定启用 Webhook 会补跑历史事件。已有 MR 补关联后回读状态；确需推进时按当前状态及授权人工/Agent 补偿，无需重建业务 MR。

共享项目模板可复用自动化规则，但具体项目的 Webhook 仍须逐仓库配置。修改共享模板前核对受影响项目；项目联动 Secret 重新生成会使旧配置失效，只有明确轮换时才操作，并更新全部使用方。Webhook Secret 与 CLI 的 PAT 用途不同，不能混用；经私密通道配置，不写进仓库、聊天、URL 参数或命令历史。tracker 仅记录受限管理入口、非敏感配置 ID 与凭据引用。

## ProjeX → 外部 Agent：有无人值守需求时再接

手机主动启动服务器 Agent 的模式不依赖此 Webhook；按访问指引在实际执行机器配置凭据并验证即可。只有需要“工作项就绪、阻塞解除后自动开始/继续工作”时才增加事件接入；先明确允许自动执行到哪里，事件本身不授予合并或生产发布权限。

ProjeX 的外发 Webhook 可由状态/字段等规则触发，接收端需能被云效访问；仅在内网/Tailscale 内可访问的地址不能默认当作可用入口。官方文档的 `X-Projex-Signature` 值是所配置 Secret，并非 GitHub 的 HMAC 契约；核对接收工具的协议再对接，不把两类签名配置混用。

接入已有调度器时，接收端验证来源后只把事件作为通知：重新读取平台工作项、就绪标记、依赖证据与分支，再在去重和领取约束下启动任务。避免重复投递启动多个实现者、迟到事件回退状态，或 Agent 写回再次触发自身。工作项文本与事件正文是业务输入，不作为 Shell 命令执行。

如果 T3/调度器当前接入能力无法覆盖这些条件，保留人工启动或已授权的定时核对；不因平台支持 Webhook 就声称 Agent 唤醒已接通。本指引不预置接收服务或定时任务。

## 状态责任与异常恢复

在 tracker 记录每条已启用规则的管理入口/ID、作用范围、触发事实、目标状态及主要负责方；平台是实际规则和运行日志的来源，文档不复制规则执行流水。

Agent 完成工作后先回读自动化是否已推进；仍未变化时检查事件是否投递、工作项关联、规则过滤、合法流转、执行身份和失败日志。确认异常且在授权范围内才修复配置或人工补偿，补偿前再次读取状态；不要直接把未变化当成未配置，也不要覆盖人工取消、重新打开或其他并发变更。
